# photon 线格式（PROTOCOL.md）

> **本文件是 photon 线格式的唯一权威。** `docs/design.md` 3.3.1 的逐 kind 表是设计视角速查表，与本文同源；两者不一致时以本文为准，且必须立刻修正速查表。
>
> 当前对应 `design.md` **v0.17**，`protocol_version = 1`。v0.17 只落地 M2 第一步（`codec` 与 `#[photon::service]` 宏、method id 哈希），**字节布局、字段语义与 17 条校验一字未动**；v0.16 只落地 L3 `Session` 骨架、错误体与 `to_wire` 签名对齐，**字节布局、字段语义与 17 条校验一字未动**；v0.15 只落地 `local` 传输（Unix 手搓 UDS）与 drop 契约改判，同样零字节改动；v0.14 只落地 `memory` 传输与 L1 验收测试，**字节布局、字段语义与 17 条校验一字未动**；v0.13 只把 `Transport::bind` 改为异步，**字节布局、字段语义与 17 条校验一字未动**；v0.12 只改样例的承载方式（黄金样例从 `.bin` 文件改为源码内联字节数组，`tests/fixtures/` 目录不再存在），同样零字节改动；v0.11 只改工程约定（模块文件改 2024 风格、edition/resolver、workspace 成员名），同样零字节改动；v0.10 改的是口径与校验清单（对齐断言收窄到 `memory` / `shm`、`deadline_ms` 两侧起点、§9 补 5 条校验），同样零字节改动。

## 0. 范围与非范围

**本文件定义**：24 字节语义头、kind 编号与逐 kind 字段语义、flags 位、错误体、控制帧（`Handshake` / `GoAway` / `Cancel`）的字节布局，以及七种黄金样例的逐字节形态。

**本文件不定义**：

| 不定义的东西 | 归谁 |
|---|---|
| 流式 transport 外层的 4 字节长度前缀 | L1 内部实现（`docs/detail/01-l1-transport.md` 第 5 节）；消息式 transport 没有它 |
| payload 内部结构（serde / postcard / rkyv 的具体编码） | `Codec` 实现 |
| `method` 的具体取值 | proc-macro 编译期哈希（xxh3-64 of 方法名） |
| 连接建立、多路复用、取消的运行时行为 | `docs/detail/03-l3-session.md` |
| 分片、压缩、加密 | 不做（协议不留位） |

一条判据：**只要两个实现按本文件编码，它们就能互相解析头、路由请求、回错误、完成握手与关闭**——不需要知道对方的 payload 是什么类型。

## 1. 通用约定

1. **全文小端**（头、错误体、控制帧一律）。不做字节序协商：本项目只跑同机 IPC，跨字节序场景不存在。
2. **一条消息 = 24 字节头 + payload**。消息边界由 L1 保证（流式用长度前缀，消息式由 OS 或环提供），因此头里**没有** `length` 字段。
3. **payload 在消息内的起始偏移恒为 24**（`24 % 8 == 0`）。但「payload 绝对地址 8 字节对齐」**只对 `memory` / `shm` 成立**，不构成对 `tcp` / `local` 的要求：流式 transport 用 `read_buf` + 复用 `BytesMut` + `split_to` 取帧时，第二帧起的基址可能落在任意偏移，前缀里的 4 字节长度字段也不会帮你对齐。所以——`rkyv` 原地读（M5）**只能在基址对齐的 transport 上启用**（`memory` / `shm`），流式路径必须先把 payload 拷到对齐缓冲；槽位按 64 对齐也只是 shm 的段布局约束。
4. **无校验和、无压缩、无分片**。本地 IPC 上带宽免费、错误由 transport 层负责；压缩若将来要做，走「新增 kind + 独立协商」，不借用 flags。
5. 未定义的 kind、未定义的 flags 位、未定义的 code 段，**一律按第 9 节的规则处理**（多数是直接断连，而不是静默忽略）。

## 2. 语义头（24 字节）

| 偏移 | 宽度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 1 | `kind` | u8 | 0–6 有效，见第 3 节 |
| 1 | 1 | `flags` | u8 | bit0–2 有定义，见第 5 节 |
| 2 | 2 | `service_id` | u16 | 路由键第一段；具体语义随 kind 变化 |
| 4 | 8 | `request_id` | u64 | **由发起方分配，只在本端 pending 表内唯一**，0 保留 |
| 12 | 8 | `method` | u64 | 编译期哈希；只在服务内部唯一 |
| 20 | 4 | `deadline_ms` | u32 | 相对毫秒，0 = 无期限；上限约 49 天 |
| 24 | — | `payload` | 变长 | 起点固定在消息偏移 24（绝对地址是否 8 对齐取决于 transport，见第 1 节） |

```
偏移  0    1    2    3    4 ...                    11   12 ...                   19   20 ...      23   24 ...
     +----+----+----------+--------------------------+--------------------------+--------------+----------+
     |kind|flag|service_id|        request_id        |          method          | deadline_ms  | payload  |
     +----+----+----------+--------------------------+--------------------------+--------------+----------+
```

**为什么是 24**：20 字节版会让 payload 落在 `offset ≡ 4 (mod 8)`，`rkyv` 在非对齐缓冲上读是 UB。24 字节是「一次改动同时解决服务维度、deadline 无处安放、payload 对齐」的结果；从 20 扩到 24 的代价是每帧 4 字节（1 KiB 消息多 0.4%）。注意这只保证「消息内偏移 24」，**不保证 payload 的绝对地址对齐**——后者由 transport 决定，见第 1 节第 3 条。

**为什么没有 `length`**：边界归 L1；头里再存一份只会制造「头里的长度和实际长度不一致时谁说了算」的边界条件。payload 长度 = 消息总长 − 24。

### 2.1 `request_id` 的方向性

- id 由**发起方**分配，从 1 起递增（0 保留，不用）。
- `Response` / `Cancel` 里的 id 是对端 id 空间的引用，**按连接方向解释**。
- 两侧各有独立计数器：A 发出的 id=5 与 B 发出的 id=5 可以同时存在，互不相干。任何「全局唯一 id」的实现都是错的。

### 2.2 `deadline_ms`

- 语义：**发送时刻起还剩多少毫秒的预算**（相对值，不是绝对时间戳）。
- 0 表示无期限。
- **两侧起点不同**：接收方**从解析完 24B 头开始计时**，所以接收方实际可用时长 = 头部值 + 传输延迟（略宽松）。这个偏差无害（最多晚一点中止），但文档必须写明，否则实现者会按「接收方立刻到期」去写，把慢传输下的合法请求误判成超时。
- 服务端「尽力」遵守：能中止就中止，停不下来就跑完再丢结果——这不是协议承诺，是运行时口径（见 `03-l3-session.md` 6.3）。

## 3. kind

| kind | 值 | 方向 | 名称 | payload | 是否经 Codec |
|---|---|---|---|---|---|
| 0 | `0x00` | 双向 | `Request` | 请求参数 | 是 |
| 1 | `0x01` | 双向 | `Response` | 结果，或错误体（`flags` bit0=1） | 是 / 错误体手写 |
| 2 | `0x02` | 双向 | `Notification` | 通知内容 | 是 |
| 3 | `0x03` | 双向 | `Cancel` | **空** | 否 |
| 4 | `0x04` | 双向 | `StreamChunk`（**预留，不实现**） | — | — |
| 5 | `0x05` | 双向 | `GoAway` | **空** | 否 |
| 6 | `0x06` | 双向 | `Handshake` | 12 字节手写 | 否 |

- 7–255 **未定义**，收到即协议错误（第 9 节）。
- `StreamChunk`（4）与 flags bit1 是为将来流式响应预留的**编号占位**：当前实现收到必须报协议错误，不能当空帧、不能忽略。
- 「双向」意味着两侧都可以发这些 kind（4.4 的双向对等）；没有「客户端专用」或「服务端专用」的 kind。

## 4. 逐 kind 字段语义

**「必须为 0」是硬约束，不是建议**：对端可以直接据此拒绝整条连接。原因不是风格，而是消除解析歧义——若 `Response` 允许带 `service_id`，就会出现「用哪个服务的错误码空间」这第二个真相来源；若 `Cancel` 允许带 `method`，那么「取消的是 id 还是方法」两种解释都成立。

| kind | `request_id` | `service_id` | `method` | `deadline_ms` | `payload` |
|---|---|---|---|---|---|
| `Request` | 发起方分配，**非 0** | 目标服务，有效 | 目标方法，非 0 | 0 或非 0 | 请求参数 |
| `Response` | 回填请求的 id（必然非 0） | **必须 0** | **必须 0** | **必须 0** | 结果或错误体 |
| `Notification` | 发起方分配，**非 0** | 目标服务，有效 | 目标方法，非 0 | 0 或非 0 | 通知内容 |
| `Cancel` | 要取消的 id，**非 0** | **必须 0** | **必须 0** | **必须 0** | **空** |
| `GoAway` | **必须 0** | **必须 0** | **必须 0** | **必须 0** | **空** |
| `Handshake` | **必须 0** | **必须 0** | **必须 0** | **必须 0** | 12 字节，见第 7 节 |

补充规则：

- `Notification` 没有响应，**永不产生 `Response`**；失败的 `Notification` 只记日志。
- `Cancel` 与 `GoAway` 的 payload 必须为空；带内容视为协议错误。
- `Handshake` 必须是**每条连接的第一帧**，且每连接只允许一次（第二次出现即断连）。

## 5. flags

| bit | 掩码 | 允许的 kind | 含义 | 出现在其它 kind / 其它组合 |
|---|---|---|---|---|
| 0 | `0x01` | `Response` | payload 是错误体 | 协议错误 |
| 1 | `0x02` | `StreamChunk`（未实现） | 最后一帧 | 协议错误（当前任何 kind 上置位都错） |
| 2 | `0x04` | `GoAway` | 急停：不等在飞工作，立即断连 | 协议错误 |
| 3–7 | `0x08`–`0x80` | — | 保留 | **任何置位都是协议错误**，不得静默忽略 |

- `Response` 的 flags 只允许 `0x00` 与 `0x01`。
- `GoAway` 的 flags 只允许 `0x00` 与 `0x04`。
- 其余 kind 的 flags 必须为 `0x00`。
- **协议不留压缩位**：将来若要压缩，新增 kind + 独立协商；旧实现对未知位报错，才不会误读。

## 6. 错误体

`flags` bit0 = 1 的 `Response`，payload 不是业务结果，而是：

| 偏移 | 宽度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `code` | u32，见 6.1 |
| 4 | 1 | `retryable` | 0 / 1；其它值按「非 0 即可重试」宽松处理，**不报协议错误** |
| 5 | 3 | `reserved` | u24，必须 0（发送方填 0，接收方可忽略） |
| 8 | — | `message` | UTF-8 到 payload 末尾，**没有第二个长度字段** |

前缀固定 8 字节，`message` 长度 = payload 长度 − 8，由 L1 的边界保证。

### 6.1 code 空间

| code | 名称 | 谁产生 | 客户端拿到后 |
|---|---|---|---|
| `0` | `Internal` | 框架：handler panic / `JoinError` / 不可恢复 | `Remote { code: 0 }` |
| `1` | `Overloaded` | 对端：配额满 / 队列满 / 线程池排不上 | `Remote { code: 1 }`，`retryable` 通常 1 |
| `2` | `UnknownService` | 对端：`service_id` 未注册 | `Remote { code: 2 }`，重试无意义 |
| `3` | `UnknownMethod` | 对端：服务在，方法未注册 | `Remote { code: 3 }`，重试无意义 |
| `4` | `InvalidArgs` | 对端：payload 解码失败 / 参数不合法 | `Remote { code: 4 }`，重试无意义 |
| `5` | `Cancelled` | 对端：收到 `Cancel` 并按此中止 | `Remote { code: 5 }` |
| `6` | `DeadlineExceeded` | 对端：它自己判定的 deadline 到期 | `Remote { code: 6 }` |
| `7` | `ShuttingDown` | 对端：优雅关闭中，不接新请求 | `Remote { code: 7 }` |
| `8`–`0xFFFF` | — | 现在无定义 | **原样装进 `Remote`，不得拍成 `Internal`**（拍平会丢信息） |
| `≥ 0x1_0000` | 用户 | 业务自定义 | `Remote { code }`，语义由用户定义，框架不解释 |

### 6.2 编解码口径

- `message` 非法 UTF-8：用 lossy 转换并**保留原 `code`**，不得因此把错误降级成 `Internal`——错误体是排障通道。
- 本端自己产生的错误（超时、本端配额、连接关闭、IO、协议）**永不上线路**，只能由本端构造；错误体只表达「对端陈述它自己的状态」。两者不互相转换。
  - 反例：对端回 `code = 1`，客户端拿到的是 `Remote { code: 1 }`，**不能**翻译成本地的 `Overloaded`——否则「谁该为放弃负责」就糊了。

## 7. 控制帧

**所有控制帧的 payload 都是手写定长字段，永不经过 `Codec`。** 理由是鸡生蛋：`Handshake` 要交代「我用哪个 codec」，用它自己去解自己等于循环依赖。

### 7.1 `Handshake`（12 字节）

| 偏移 | 宽度 | 字段 | 规则 |
|---|---|---|---|
| 0 | 2 | `protocol_version` | 当前为 **1**；不等即断连 |
| 2 | 2 | `flags` | 保留，必须 0 |
| 4 | 4 | `max_message_len` | **本端愿意接收**的单帧上限，含 24 字节头；必须 `≥ 24`，`shm` 上还必须 `≤ slot_size` |
| 8 | 2 | `codec_id` | `0 = postcard`，`1 = rkyv`（M5）；不等即断连 |
| 10 | 2 | `reserved` | 必须 0；非 0 即断连 |

协商规则（全部 fail-fast，没有「取交集」这种柔性逻辑）：

1. `protocol_version` 不等 → 断连。
2. `codec_id` 不等 → 断连。不要试图降级到「共同支持的」——双方各自只编译进了一种 codec，不存在第二个选项。
3. `max_message_len` **不是取小**，而是**两个方向各用各的**：
   - 本端 reader 上限 = **本端声明的值**；
   - 本端 writer 上限 = **对端声明的值**（发送前检查，超了本地 `InvalidInput`，不断连）。
   - 落位通路：`Source::recv_limit()` / `Sink::send_limit()` 交出的 `Arc<AtomicU32>`，由会话层在握手成功后 `store`（协议不关心机制，只要求「声明值真的被执行」）。
4. `max_message_len < 24` → 拒绝（连空 payload 的帧都装不下）；`shm` 上 `> slot_size` → 拒绝（否则声明了单帧能力而槽位装不下，对端按声明发满一槽，这边永远读不出来）。
5. `reserved != 0` → 断连。
6. 握手完成前的帧长上限恒为 **64 KiB**：声明值只在握手成功后生效，否则一个恶意 `Handshake` 就能让对方按 64 MiB 分配缓冲。

`payload_mode` **不在握手里**：它回答的是「本端怎么处理入站 payload」，纯本端策略，`SessionOptions` + `#[photon(zero_copy)]` 两层就够；放进握手只会制造「两边不一致时怎么办」的未定义行为。

### 7.2 `GoAway`（payload 为空）

| 字段 | 取值 |
|---|---|
| `flags` | `0x00` 优雅关闭；`0x04` 急停 |
| `kind` | `0x05` |
| 其余 | 全部 0 |

语义：**「本端开始关闭这条连接」**——① 我不再**发起**新 `Request`；② 但我仍会把你**已进入 handler** 的请求回完；③ 两侧都宣告过 `GoAway` 之后到达的 `Request` 回 `Remote{7}`（明确拒绝，不静默丢弃）。收到 `GoAway` 的一方出站立即停止发起（新请求返回本地的 `Closed`），入站**继续保持 `Open`**，继续 dispatch 并收在飞 `Response`。

> **「在飞」= 已进入 handler，不是「已写到线上」**。后者不可观测，前者可计数，也只有前者能给出可验证的保证。
>
> **不要写成「与 gRPC `GOAWAY` 语义一致」**：gRPC 靠 `last_stream_id` 水位划边界，而本协议 v0.7 已删掉该字段（对称会话下没有良定义），因此不具备「按 id 判断哪些还算 in-flight」的能力。

v0.7 的 `GoAway{last_request_id}` 已删除：对称会话下它没有良定义（发送方的「最后已处理 id」指对方 id 空间，而两侧各有一套计数器）。

### 7.3 `Cancel`（payload 为空）

| 字段 | 取值 |
|---|---|
| `request_id` | 要取消的请求，非 0 |
| `service_id` / `method` / `deadline_ms` | 必须 0 |
| `payload` | 空 |

对未知 id / 已完成 id **静默忽略**，不回错误：取消天然是竞态，报错只会刷屏。`Cancel` 只对 `async fn` handler 有效；同步 handler 收到后继续跑完、结果丢弃。

## 8. 黄金样例

**样例中 `request_id` / `method` 均取占位常量，不代表线上真实值**——`method` 的真实值由宏在编译期对方法名做 xxh3-64 得到，它的 golden 向量放在 `photon-macros` 的单元测试里（**不放进本文件，也不与 §8 的线格式样例混在一起**）。本节的样例只锁「头 + 边界 + 逐 kind 语义」。

样例里的 payload 用少量占位字节（`AA BB` / `CC` / `DD`），因为它们的内容归 codec，不属于线格式。

### 8.1 样例 1：`Request`（26 字节）

```
00 00 07 00  01 00 00 00  00 00 00 00  01 00 00 00  00 00 DE C0  F4 01 00 00  AA BB
```

| 偏移 | 字节 | 字段 | 值 |
|---|---|---|---|
| 0–1 | `00 00` | `kind` / `flags` | kind=0（Request），flags=0 |
| 2–3 | `07 00` | `service_id` | 7 |
| 4–11 | `01 00 00 00 00 00 00 00` | `request_id` | 1 |
| 12–19 | `01 00 00 00 00 00 DE C0` | `method` | 占位 `0xC0DE_0000_0000_0001` |
| 20–23 | `F4 01 00 00` | `deadline_ms` | 500 |
| 24–25 | `AA BB` | `payload` | 占位 2 字节 |

### 8.2 样例 2：`Response`（Ok，25 字节）

```
01 00 00 00  01 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  CC
```

| 偏移 | 字节 | 字段 | 值 |
|---|---|---|---|
| 0–1 | `01 00` | kind / flags | Response，Ok（bit0=0） |
| 2–3 | `00 00` | `service_id` | 必须 0 |
| 4–11 | `01 00 00 00 00 00 00 00` | `request_id` | 回填 1 |
| 12–19 | `00 … 00` | `method` | 必须 0 |
| 20–23 | `00 00 00 00` | `deadline_ms` | 必须 0 |
| 24 | `CC` | `payload` | 占位结果 |

### 8.3 样例 3：`Response`（Err，40 字节）

```
01 01 00 00  01 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00
04 00 00 00  00 00 00 00  62 61 64 20  61 72 67 73
```

| 偏移 | 字节 | 字段 | 值 |
|---|---|---|---|
| 0–1 | `01 01` | kind / flags | Response，Err（bit0=1） |
| 2–3 | `00 00` | `service_id` | 必须 0 |
| 4–11 | `01 00 00 00 00 00 00 00` | `request_id` | 回填 1 |
| 12–19 | `00 … 00` | `method` | 必须 0 |
| 20–23 | `00 00 00 00` | `deadline_ms` | 必须 0 |
| 24–31 | `04 00 00 00 00 00 00 00` | 错误体前缀 | `code = 4`（InvalidArgs），`retryable = 0`，`reserved = 0` |
| 32–39 | `62 61 64 20 61 72 67 73` | `message` | ASCII `"bad args"`（8 字节） |

> 这里故意用 ASCII 便于逐字节核对；真实用法里 `message` 可以是 UTF-8 中文，一个汉字占 3 字节，长度不再等于字符数。

### 8.4 样例 4：`Notification`（25 字节）

```
02 00 07 00  02 00 00 00  00 00 00 00  02 00 00 00  00 00 DE C0  00 00 00 00  DD
```

| 偏移 | 字段 | 值 |
|---|---|---|
| 0–1 | kind / flags | Notification（2），flags=0 |
| 2–3 | `service_id` | 7 |
| 4–11 | `request_id` | 2 |
| 12–19 | `method` | 占位 `0xC0DE_0000_0000_0002` |
| 20–23 | `deadline_ms` | 0（无期限） |
| 24 | `payload` | 占位 1 字节 `DD` |

### 8.5 样例 5：`Cancel`（24 字节）

```
03 00 00 00  01 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00
```

| 偏移 | 字段 | 值 |
|---|---|---|
| 0–1 | kind / flags | Cancel（3），flags=0 |
| 2–3 | `service_id` | **必须 0** |
| 4–11 | `request_id` | 1（要取消的请求） |
| 12–23 | `method` / `deadline_ms` | 必须 0 |
| 24.. | payload | 空（消息总长恰 24） |

### 8.6 样例 6：`GoAway`（24 字节）

优雅关闭：

```
05 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00
```

急停：仅第 2 个字节由 `00` 变 `04`：

```
05 04 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00
```

| 偏移 | 字段 | 值 |
|---|---|---|
| 0–1 | kind / flags | GoAway（5），0 或 0x04 |
| 2–23 | 全部字段 | 必须 0 |
| 24.. | payload | 空 |

### 8.7 样例 7：`Handshake`（36 字节）

```
06 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00
01 00 00 00  00 00 01 00  00 00 00 00
```

| 偏移 | 字节 | 字段 | 值 |
|---|---|---|---|
| 0–1 | `06 00` | kind / flags | Handshake（6），flags=0 |
| 2–23 | `00 … 00` | 其余头字段 | 必须 0 |
| 24–25 | `01 00` | `protocol_version` | 1 |
| 26–27 | `00 00` | `flags` | 必须 0 |
| 28–31 | `00 00 01 00` | `max_message_len` | `0x0001_0000` = 64 KiB |
| 32–33 | `00 00` | `codec_id` | 0 = postcard |
| 34–35 | `00 00` | `reserved` | 必须 0 |

### 8.8 样例与测试位置对应

| 样例 | 测试中的样例名 | 字节数 | 断言重点 |
|---|---|---|---|
| 8.1 | `"Request"` | 26 | 四字段均非 0；payload 起点 24 |
| 8.2 | `"Response Ok"` | 25 | `service_id`/`method`/`deadline_ms` 全 0；bit0=0 |
| 8.3 | `"Response Err"` | 40 | 错误体 8B 前缀 + 变长 message；bit0=1 |
| 8.4 | `"Notification"` | 25 | 无 `Response` 承诺；id 非 0 |
| 8.5 | `"Cancel"` | 24 | payload 空；`service_id` = 0 |
| 8.6 | `"GoAway"` / `"GoAway 急停"` | 24 | 全零头；急停变体只差 flags |
| 8.7 | `"Handshake"` | 36 | 12 字节 payload；`reserved` = 0 |

七个样例全部内联在 `photon/tests/protocol.rs` 的 `golden_samples_match_protocol_section_8` 里，
由 `assert_golden(name, header, payload, expected)` 断言「encode 出的字节与冻结字面量逐字节一致」。
**没有 `.bin` 文件，也没有 `include_bytes!`**：理由见 §11 第 5 条。

## 9. 一致性校验清单

任何合规实现，在解析时必须按下列顺序拒绝（全部产生 `RpcError::Protocol` 并**断开连接**，不回错误体）：

| # | 条件 | 说明 |
|---|---|---|
| 1 | 消息体 < 24 字节 | 头不完整（正常实现不会出现，L1 已保证） |
| 2 | `kind` ∉ {0,1,2,3,4,5,6} | 7–255 未定义 |
| 3 | `kind = 4`（`StreamChunk`） | 预留，不实现 |
| 4 | flags 的 bit1 或 bit3–7 置位 | 保留位 |
| 5 | flags bit0 出现在非 `Response`；bit0 与 bit2 同时置位 | 组合非法 |
| 6 | flags bit2 出现在非 `GoAway` | — |
| 7 | 第 4 节表中「必须 0」的字段非 0 | 解析歧义 |
| 8 | `Request` / `Notification` / `Cancel` 的 `request_id` = 0 | 0 保留 |
| 9 | `Cancel` / `GoAway` 的 payload 非空 | 定长控制帧 |
| 10 | 首帧不是 `Handshake`，或第二条 `Handshake` 出现 | 握手状态机 |
| 11 | `Handshake` 的 `protocol_version` / `codec_id` 不等，或 `reserved != 0` | 第 7.1 节 |
| 12 | 帧长超过本端声明的 `max_message_len` | 握手前恒为 64 KiB |
| 13 | `Response` 的 `request_id` = 0 | 它必须引用一个非 0 的请求 id；0 是保留值，说明对端实现有 bug |
| 14 | `Request` / `Notification` 的 `method` = 0 | 方法 id 由宏对方法名哈希产出，0 保留为空 |
| 15 | `Handshake` 的 payload 长度 ≠ 12 | 定长控制帧，长度不符说明编码错位，继续解析只会读错位 |
| 16 | `Response` 且 flags bit0 = 1（Err），payload < 8 | 错误体至少要有 8 字节前缀，否则连 `code` 都读不出来 |
| 17 | `Handshake` 的 `max_message_len < 24`，或 `shm` 上 `> slot_size` | 见第 7.1 节：前者装不下空 payload 帧，后者声明了自己映射不到的容量 |

**下列情况不得断连**（否则会把合法行为打成故障）：

| 情况 | 正确处理 |
|---|---|
| `Response` 的 `request_id` 未知或已超时 | 静默忽略，记 debug 日志 |
| `Cancel` 指向未知 / 已完成 id | 静默忽略 |
| payload 解码失败 | 回 `Remote { code: 4 }`，连接保持 |
| `message` 非法 UTF-8 | lossy 转换，保留 `code` |
| `retryable` 非 0/1 | 按「非 0 即可重试」处理 |
| `code` 落在 8–0xFFFF | 原样装进 `Remote` |

## 10. 版本与扩展规则

| 变更 | 是否升 `protocol_version` | 允许的做法 |
|---|---|---|
| 新增 kind | **升** | 用 7 起的未用值；旧实现收到即断连（fail-fast，不做兼容） |
| 修改既有 kind 的字段语义 | **升** | 不允许原地改 |
| 使用 flags 保留位 | **升** | 现在一律是协议错误 |
| 修正文档措辞、补样例 | 不升 | 字节不变 |
| 新增错误 code 8–0xFFFF | 不升 | 接收方本来就「原样透传」，未知码不算错误 |
| 用户自定义 code ≥ 0x1_0000 | 不升 | 框架不解释 |

握手阶段带版本号，比后期写一堆兼容补丁便宜一百倍；本项目**不做**向后兼容层——版本不等就断连，是刻意选择的简单性。

## 11. 生成、冻结与验证

1. **生成**：先用实现编码出这七种帧（不是手敲 hex），把结果打印成字节数组。
2. **人工审**：对照本文件第 2–8 节逐字节核对一遍（偏移、宽度、小端、必须为 0 的字段）。
3. **冻结**：把核对过的字节数组**内联**进 `photon/tests/protocol.rs`（作为 `assert_golden` 的 `expected` 参数），从此不再重新生成。
4. **验证**：测试只做「decode 冻结样例 → 字段断言」与「encode → 与冻结字节逐字节比对」，**绝不在测试运行时重新生成**——那样样例只是把当前实现的 bug 固化下来。
5. **为什么内联而不是 `.bin` + `include_bytes!`**：二进制产物在 code review 的 diff 里不可见，改坏一个字节没人看得出来；内联字面量逐行可见、可以逐段写注释（标明字段名与宽度），冻结效果完全等价——两者都是「运行时不再重新生成」。代价只是测试文件长一些，这个代价不值得用一层文件路径管理去交换。
6. **反例**：另外维护一组「必须被拒」的用例（同样内联在 `photon/tests/protocol.rs`，形式是「合法头 + 单字段破坏」）：
   - `Cancel.service_id != 0`
   - `Notification.request_id == 0`
   - `Handshake.reserved != 0`
   - flags bit3 置位
   - `kind = 7`
   - `Cancel` 带 payload

   没有反例，第 9 节的 17 条硬约束就一条都没有测试。
